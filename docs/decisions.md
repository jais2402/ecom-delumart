On 20 November 2026 the owner asked for open decisions to be made for them. Each choice below is the safer or cheaper default and can be reversed; the last column says what reversing it involves. Decisions that need money, a legal opinion or an account in the owner's name are listed separately because they cannot be made by anyone else.

### 14. Ratings and reviews

| Rule | Choice |
|---|---|
| Who may review | Only a player who owns the product (an active ownership row, created by the purchase). Never an owner of the selling company. No job, seed or NPC path writes reviews. |
| How many | One review per player and product. Saving again edits it: a new version is kept and the review shows "Edited". The author can delete it; the text and versions are deleted for real. |
| What | Rating 1 to 5 (required); title up to 80 characters, on one line, and review up to 1,000 (optional). `REVIEW_RULES` in `packages/core/src/review` is the one source of these numbers; the database reads the same configuration keys with those defaults, clamped (migration 0079). |
| Text screening | The listing and store text rules (`packages/core/src/screening`). Anything not screened OK is refused with per-field reasons, because there is no human review queue for reviews; brand-like or shouted text is refused too. No submitted text is echoed. Since review round 1 the shared rules also refuse hidden format and separator characters (a joiner inside an Indic word excepted), read digits of every script as digits, and treat any dotted domain-like word as a link. The database (migration 0079) refuses the same as a backstop. |
| Limits | 10 review writes an hour per account (web rate limit, `core.rate_hit`). |
| Public display | Average to one decimal from integer sum and count (sent as `averageTenths`, never a float), count, five distribution bars, newest reviews ten per page. Each shows stars, title, text, the author's public handle if they set one, a "Verified owner" badge and the day (store reporting time zone). Never a user id, order, purchase time or review id. |
| Timing | A review is public only from the reporting day (Asia/Kolkata) after the one it was written in (migration 0079). The author sees it at once, marked "Visible to others from tomorrow"; the average and count include public reviews only. |
| Cards and rails | A separate public endpoint returns summaries for up to 100 product ids; the catalogue response is unchanged. |
| Moderation | The Super Admin hides a review with a reason and can restore it (audited). Hidden reviews leave the list and the average; the author still sees theirs as hidden, with the reason. Deleting and writing again does not undo a hide. |
| Housekeeping | The daily purge also scrubs codes that expired unused and deletes closed bank inbox rows older than `bank_inbox_retention_days` (30). The payment screens' polling intervals, page size and retry fallback live in `PAYMENT_UI_CONFIG` (client-safe), not in components. |
| Analytics | `review_submitted` and `review_hidden` server events, with no props, user id or text. |
| Why the next day (decided in review round 1) | A review under a public handle says that this player owns the product, which is its purpose. The seller sees each order to the minute with no buyer. Publishing a review the moment it is written (or the minute after the purchase) would let a seller match a handle to an order for a product that sells rarely; publishing only the next day, and showing only the day, decouples the review from the order's time, so a review says no more than "bought on or before that day". |
| Not in this round | Reporting a review (use the console for now), helpfulness votes, photos, seller replies. |

### 15. Sale price, reference price and merchant-funded delivery

| Point | Choice |
|---|---|
| What a sale is | A lower live price for a published listing, put there by the owner (`PUT /api/v1/studio/products/{id}/sale-price`, migration 0081). It is a new product version at the sale price, so quotes, carts, purchases and the 5% fee all use it through the one pricing function; outstanding quotes fail at pay with `CART_CHANGED` (US-08). The list price it returns to is kept in `core.product_sale` (one open sale per product; no role reads or writes it directly). The fee is on the sale price (R6.6: "what the seller is selling it for"). |
| Sale price is not a "discount given" | "Discount given" in finances is the seller-funded coupon discount only (R6.6, R8). A sale shows up as a lower gross, never as a discount, so nothing is counted twice. |
| Ending a sale | Manual only (`DELETE` on the same route): a new version at the list price. No scheduled end date (the PRD has none). |
| List price during a sale | `core.product_set_price` is refused (`NOT_EDITABLE`) while a sale is open: end the sale first. Otherwise the price a sale returns to could move under it. |
| The reference ("was") price (changed in review round 1, migration 0083) | The lowest-prior-price rule (EU Omnibus style). The reference shown is the LOWEST price the listing was published at (a list or a sale price, any version) in the `reference_price_lookback_days` (30) before the current price took effect, shown only when it is strictly above the current price and the listing was published for at least `reference_price_min_hours` (24) within that window. A listing published for less than 30 days uses its whole history. A hidden period counts as no price: it neither sets the minimum nor breaks the 24 hours. It is derived, never stored, by `core.reference_price` (SQL) and `referencePrice()` (TypeScript, `packages/core/src/pricing/reference-price.ts`), which a database property test (random publish, price, sale and hide histories) holds identical. This replaces the first reading ("the price right before was live for 24 hours"), which let a seller raise the price, wait 25 hours and show a fake "Was"; both review attack replays are tests. A sale ended and restarted at the same price shows none while the first sale is inside the 30 days. |
| Asking for a reference | `requireReference: true` makes the command refuse with `REFERENCE_PRICE_INELIGIBLE` (HTTP 422), changing nothing, when no reference would show. Without it the sale applies and the shop shows only the current price. The owner's listing view carries `referenceCeilingPaise` (a sale price strictly below it shows exactly that "Was"; at or above it shows none; null until the listing has been published 24 hours) and `canShowReference`, so the screen can say what will happen. |
| Allowance | `price_changes_per_product_per_day` (20) within `price_change_window_hours` (24), per listing, counted over list price changes, sale starts, sale price changes and ends: beyond it (for everything but an end) `RATE_LIMITED`. Ending a sale is never blocked by it, so a mistake can always be fixed, but the end COUNTS toward it (changed in review round 2): at most `cap` starts, changes and list price changes plus the ends that follow, so ten start/end cycles use up the default 20. A same-price call writes and counts nothing. Stops a price being flipped to keep quotes failing or to manufacture a reference. |
| Free delivery needs a fundable price | A sale price, a list price change (with free delivery on) and turning free Standard delivery on are refused with `FREE_DELIVERY_UNFUNDED` (HTTP 422) when the resulting live price could not fund the Standard fee out of the seller's proceeds (smallest whole-rupee L with L - floor(L x fee% / 100) >= the Standard fee; ₹1,053 at 5% and ₹1,000). The message names the minimum; `core.min_free_delivery_price` (SQL, from configuration) and `minPriceForFreeDelivery()` (TypeScript) are the same arithmetic and tested against the pricing function. Coupons can still push a quote under it; that stays `DELIVERY_UNAVAILABLE` at quote time. The draft path is covered too (migration 0084): creating or editing a draft with the flag on, and submitting one, are refused; as backstops for a configuration that moved after submission, approval (screening or Super Admin) REJECTS the submission with the minimum in its reason (a rejected revision leaves the live listing untouched) and publishing refuses, so a listing never goes live unbuyable. The price minimum is the configured `price_min_paise` on both sides (`minPriceForFreeDelivery(cfg, minPricePaise)`). |
| Configuration in the studio | The owner's listing view returns `sale.rules`: reference minimum hours, lookback days, daily allowance and window, changes left, price bounds, the minimum price for free delivery. The Pricing and Shipping pages read them; they hold no constants. The keys are written into the existing configuration versions IN PLACE with the defaults the functions used (a key already present wins), not as a new version: a new version would fail every open checkout session at pay, because a session is pinned to the configuration it was quoted under. Values are clamped before any integer cast so a huge or zero value cannot error a public read: lookback 1 to 365 days, minimum hours 1 to lookback x 24, change window 1 to 8,760 hours (a negative number is not a configuration value, so the default applies). |
| Workers | R8 says a worker cannot change a live price. There are no worker seats yet; every studio command finds the company by `owner_user_id`, so a non-owner gets `NOT_FOUND` (another company's listing) or `COMPANY_FEE_REQUIRED`. Tested as such; revisit when seats exist. |
| Free Standard delivery | Per product (R8 Shipping row), toggled in the product editor and on the new Shipping page. A seller order is delivery-free only when every line in it offers it (LLD §5.1); otherwise the buyer pays the fee. If the proceeds cannot fund the fee, the quote is refused (`DELIVERY_UNAVAILABLE`, existing rule), which a deep sale price can trigger. The fee is taken from the seller and goes to SINK. |
| Events | `sale_price_set` (start or change) and `sale_price_ended` are domain events in the outbox with ids and prices only. They are not product-analytics events: the analytics allow-lists (0052) are unchanged. |
| Finances | `core.earnings_totals` gains `discountPaise`. Each period shows gross (after seller discounts), discounts given, marketplace fees, merchant-funded delivery and net once each; net = gross - fees - merchant-funded delivery and equals the owner's ledger credit. Order times stay delayed by a minute (0060). |
| Cart preview and coupons | When a cart cannot be priced even without its coupon, the preview now reports the coupon's refusal first, as checkout does. Found by the extended 50-random-cart test. |
| Delulu Plus | Not built. The pricing function's member flag is untouched: a member's Standard fee is 0, so a merchant-funded Standard delivery then costs the seller 0. |

### 16. Super Admin delayed actions and configuration versions

Migration 0090; `packages/core/src/console-config`; routes under `/api/v1/admin/actions` and `/api/v1/admin/config`; console pages Pending actions and Configuration.

| Rule | Choice |
|---|---|
| Queue | `audit.pending_action`. A Super Admin proposes an action of an allow-listed kind with a reason (5 to 500 characters, no contact details or links); it waits `admin_action_delay_seconds` (default 24 h, clamped to 1 h .. 7 days, so a configuration value of 0 cannot remove the delay). The delay is read at proposal time and is not itself changeable through the queue. |
| Kinds | Only `config.set` now. Platform coupon budgets, minting, reversals and research exports are not built; each is added as a kind in a new migration (validator and executor) without changing the queue. |
| Allow-listed keys | `fee_percent` (0 to 20), `delivery_fee_paise.STANDARD`, `.EXPRESS`, `.ZAP` (0 to ₹1,00,000, paise as decimal strings). Ceilings are safety rails in the registry (`CONFIG_KEYS` and `core.config_key_registry()`, checked equal by a test), chosen so checkout cannot break; a test buys at every minimum and every maximum and reconciles. Grants, thresholds, price bounds and limits are not changeable from the console. |
| Proposal checks | Super Admin only; a sign-in within five minutes (`REAUTH_REQUIRED`); a value equal to the current one is a conflict; one waiting change per key; at most `admin_action_open_max` (20) waiting at once. |
| Cancelling | Allowed while the action is still `QUEUED`, even if it is overdue and only waiting for the next job run. It does not need a recent sign-in, because it only removes a change (an attacker who cancels the owner's change causes nuisance, not damage). |
| Execution | The jobs endpoint's `pending_action.execute` step (`core.admin_actions_execute_due`, the only function `app_jobs` gained): due, queued rows in `not_before` order, `FOR UPDATE SKIP LOCKED`, each in its own sub-transaction. The payload hash, the proposer's role, the kind and the bounds are checked again. A failure marks the action `FAILED` with a code and is final (never retried); a lock timeout leaves it queued. Cancelled and finished actions never run. |
| New version | A new `core.config_version`: the newest version's values plus the one change; an old version is never updated. Locks: pending rows, then the base version (`FOR NO KEY UPDATE`, so purchases never wait), then the audit chain head. Two changes in one run therefore both survive. |
| Effective time | 30 seconds after the write (`config_apply_grace_seconds`), because a checkout session opened while the executing transaction is uncommitted would otherwise be priced under the old version yet start after the new one, and the pay check of 0016 would refuse it. Orders keep their version (`order_group.config_version`); a session opened before and paid after the change still prices under its own version (tested). |
| Record | `audit.config_change` (the ConsoleConfigChange of R10: area, before, after, versions, actor, approver `DELAYED_EXECUTION`, reason), audit rows for propose, cancel, execute and fail, and an outbox row per step with ids, kind, key and time only. The version's `note` carries the key, never the reason (application roles can read it). |
| Email | Not built (the app has no sender). `TODO(email-sender)`: the outbox relay turns `admin_action_proposed`, `_cancelled`, `_executed` and `_failed` into the alert email of R16.6. The Super Admin sign-in alert and the passkey are also not built. |
| Analytics | `console_config_changed`, no props, no user id, written only by the executor; `analytics.record_event` refuses it from any caller. |
| Announcement | `core.announcement`: the setting and the new value, no reason, no person, no old value. `GET /api/v1/announcements` is public (30 s shared cache, never reads the session). The storefront shows "Store news" for 72 hours (`announcement_window_hours`), at most three. |
| Local helper | `pnpm dev:expedite-admin-actions` (owner connection, loopback database and server only, refuses production; a test checks the refusals) makes waiting actions due, calls the signed jobs endpoint and lets the new version take effect. It is not an app route. |

### 17. DeluluPay simulator

Migrations 0100 to 0103; `packages/core/src/pay`; routes `POST /api/v1/checkout-sessions/{id}/challenge` and `.../challenge/verify`, `POST /api/v1/attempts/{id}/cancel`, `GET /api/v1/attempts/{id}`, `GET /api/v1/bank/inbox`, `GET /api/v1/payment-methods`, `GET /api/v1/account/payments`, `GET|POST /api/v1/admin/payment-methods`; account pages Payments and Bank inbox.

| Point | Choice |
|---|---|
| Route shape | PRD R10 puts the challenge routes on the checkout session; LLD §8.2 puts them on the attempt. The PRD and the build brief win: `POST /checkout-sessions/{id}/challenge` and `/challenge/verify` act on the session's newest PENDING attempt of the signed-in payer. The attempt's own `POST /attempts/{id}/pin` (card) is unchanged. |
| Which sessions | The new methods apply to `PRODUCT_PURCHASE` sessions. A company registration still takes BALANCE or CARD (its commit function, 0034, is unchanged); NET_BANKING and DELULUPAY_ID there are refused with `METHOD_UNAVAILABLE` and the "no fictional money moved" wording. Memberships and warehouse purchases do not exist yet. |
| DeluluPay ID | The PRD says "pick or type" an ID. The typed ID must be the payer's own (`bank_account.upi_style_id`): an approval request goes to the payer's own inbox only, so no one can send a collect request to someone else. A typed ID that is another player's, or has any other ending, is `VALIDATION_FAILED` and creates nothing. Reserved test IDs (`testpay.<name>@delulu`) are the only exception (see scenarios). |
| The code | Generated by the database from its random source, six digits, valid `challenge_ttl_seconds` (180), single use, bound to its attempt (the hash includes the attempt id, so a code cannot be used on another attempt). Only a hash is stored in `core.payment_challenge`, and no application role can read even that column (column-level grants). The plaintext is shown only in the payer's bank inbox (`core.bank_inbox_message`, read by `core.my_bank_inbox`), and is set to NULL the moment the challenge ends (passed, expired, locked, cancelled, replaced by a resend). It is in no event, outbox row, audit row, idempotency record, log or other response; tests search for it. The code is part of the experience, not a second factor (R4.4): the signed-in session stays the authority. |
| Tries and resend | Three wrong tries in all per payment attempt (`challenge_tries`); a resend does not reset them. The third fails the attempt with `CHALLENGE_LOCKED`. A new code may be asked for `challenge_resend_seconds` (30) after the last, at most `challenge_codes_per_hour` per account per hour, default 10 after review (approvals and codes count together, by decision), counted per account so a stranger cannot use up someone else's. A code presented after it expired fails the attempt with `CHALLENGE_EXPIRED` (the PRD lists "code expired" as a decline reason). A wrong code that is not the last returns `CHALLENGE_FAILED` with the tries left and the attempt stays open. All five numbers are configuration keys with defaults and clamps (invariant 10). |
| Rate limits | The database caps above, plus the web server's per-ACCOUNT limits on issuing and verifying. There is deliberately NO per-address counter on these routes (review, decided by the coordinator): one free account at its actor limit would otherwise fill the address counter and lock out everyone behind a shared address, and with no peer address known every request would share one global counter. A test checks that one account exhausting its limits does not affect another on the same or an unknown address, and that no challenge rule is keyed by address. |
| Status model | No new stored state. The stored `PENDING / SUCCEEDED / FAILED` plus `authenticated_at` and the existence of a challenge give Created, Authenticating, Authorised, Captured, Failed and Refunded (`core.payment_display_status`, equal to `displayStatus()` in core, checked for every combination). A PENDING attempt whose session ended shows as Failed with `CHECKOUT_EXPIRED`. Refunded is shown when every seller order of the attempt's order group was reversed by staff; there is no player refund button. |
| Stored failure codes | `INSUFFICIENT_FUNDS`, `CARD_FROZEN`, `CARD_REPLACED`, `CHALLENGE_FAILED`, `CHALLENGE_EXPIRED`, `CHALLENGE_LOCKED`, `CANCELLED` (cancelled by you, or a declined approval), `METHOD_UNAVAILABLE`, `METHOD_LIMIT_EXCEEDED`, `BANK_UNAVAILABLE`, `CHECKOUT_EXPIRED` (session expired), and the pay step's own refusals. The wording lives in `DECLINE_REASONS` (core) and every message ends "No fictional money moved." An unknown code gets the generic text and is never echoed. |
| Method configuration | `core.payment_method_config`: append-only versions per method (enabled, display order, per-attempt and per-day limit in paise, optional maintenance window). No application role has any privilege on it. Changes are a second kind in the delayed queue, `payment_method.set` (24 hours, cancellable, recent sign-in, one waiting change per method), with no faster path. A change is judged by its END STATE, when proposed and again when it runs (so of several queued actions the last one that would leave nothing usable is refused, FAILED with `CONFIG_VALUE_INVALID`): afterwards at least one method must be enabled, switched on, outside a maintenance window at any time during the window being set (or at this instant when none is set), and have per-attempt and per-day limits at or above the floors `payment_limit_floor_attempt_paise` (₹1 lakh) and `payment_limit_floor_day_paise` (₹10 lakh), clamped configuration keys (0104). The proposal's and the execution's audit rows carry the full proposed values (no person). It takes effect when it runs (no grace period: a payment method is checked at attempt and at pay, not pinned to a quote). The per-day limit is the payer's SUCCEEDED payments of that method that were PAID since the start of the UTC day (order group or company registration creation time, not the attempt's creation time, so an attempt made at 23:59 cannot dodge it) plus this amount. A company registration is gated at pay like a purchase (its commit function re-created from 0034 with one added call). |
| The gate | `core.payment_method_gate` is the single check, called when an attempt is created and again inside `core.commit_purchase` before anything is written (a refusal there fails the attempt with the code and debits nothing). It takes the payer's advisory lock first, before any row lock of LLD §4, so two concurrent payments cannot both pass the same daily total. The kill switches stay and gate their method: `payments_card`, `payments_netbanking` and the new `payments_delulupay_id`. |
| Pay path | `core.purchase_write` (0018) and `core.commit_purchase` (0058) are re-created with the smallest change: the method allow-list and the shared switch lock. Pricing and the ledger are untouched: amounts still come only from the pricing function, journals still sum to zero, and a test compares a DeluluPay ID purchase with a balance purchase. |
| Test scenarios (R4.6) | `INSUFFICIENT_FUNDS`, `BANK_UNAVAILABLE`, `SLOW_BANK`, `CODE_LOCKOUT`, `CODE_EXPIRED`, chosen by a reserved test ID or an explicit `scenario`. They act at the authentication step only, never in pricing, the ledger or the pay transaction, and are never random. They are open only when the owner sets `deployment_setting 'payments.test_scenarios'` to `on` (`pnpm dev:setup` does; the migration leaves it `off`; no application role can change it) or the actor is a staff test account (`is_test_account`). Otherwise the request is `VALIDATION_FAILED` and nothing is created. The forced INSUFFICIENT_FUNDS decline is stored as `TEST_INSUFFICIENT_FUNDS` and shown as "Test scenario: insufficient funds", so it never reads as a real reason; a slow bank's code is not shown in the inbox before it answers. A player's own ID can never be a reserved ID (a check constraint; handles never contain a dot). |
| Real payment data (R4.5, US-37) | `looksLikeRealPaymentData` (core) is applied to the two free-text fields of checkout: the coupon code (before any lookup, so a pasted card number is refused without a database call and never echoed) and the DeluluPay ID. It flags 13 to 19 digits however separated (so a pasted card number is refused whatever the dashes), an expiry written MM/YY or MM/YYYY (or MM-YY as the whole text; a code such as SAVE-10-25 is accepted), any handle at another provider, an expiry, and the words CVV, PIN, OTP, password. It leans strict: a false positive only asks for different text. The challenge code is exactly six digits and the request schemas reject unknown fields, so a `cardNumber`, `cvv` or `expiry` is a validation error. The only PIN field remains the labelled Delulu PIN. |
| Analytics | `payment_method_selected`, `payment_challenge_issued`, `payment_challenge_passed`, `payment_challenge_failed`: server events with one prop, `method` (one of four names); no user id, visitor, code or amount. |
| Not in this round | Pay on delivery, further banks, a console screen for the method settings (the API and the queue exist), a refund screen, SMS of any kind. |
