DeluluMart low-level map

The build-level view: how the data is shaped, exactly what the payment transaction does, where each rupee is posted, and the states things move through. The full reference, with every table, algorithm and endpoint, is docs/system-design/low-level-design.md.

2. Inside the pay transaction

Everything below happens in one database transaction. If any step fails, nothing is saved.

Steps

  1. Check the retry keySame key and same request returns the stored result. Same key with a different request is refused.
  2. Check the kill switchIf purchases are switched off, or the switch cannot be read, stop.
  3. Lock rows in the fixed orderThe list on the right. Waiting is capped at 2 seconds, then the client retries.
  4. Re-check everythingSession open, payment authenticated, card active, price and version unchanged, not already owned, coupon valid, balance enough.
  5. Recompute the totalOne pricing function. If it differs from the quote, stop with "cart changed".
  6. WriteJournal and postings, orders, ownership, stock issue, coupon use, shipments, wallet balances, creator unlock if below ₹1 crore.
  7. Queue follow-up and commitOne outbox row, the stored result for the retry key, then commit.

Lock order

  1. checkout_session one outcome per checkout
  2. coupon, promo_campaign cap and budget
  3. membership benefit still valid
  4. company limits and counters
  5. warehouse capacity
  6. product stock total, current version
  7. inventory_unit the exact unit sold
  8. virtual_card status, PIN counters
  9. wallet buyer and every seller
  10. entitlement creator and brand unlock

Every transaction takes locks in this order, lowest id first within a step. That is what prevents deadlocks and makes "last unit" and "freeze versus pay" races resolve cleanly.

3. Where the money is posted

Worked example: a ₹2 crore item with a 10% merchant coupon and ₹1,000 Standard delivery. Amounts in rupees; the database stores paise.

4. Card checkout, call by call

sequenceDiagram
  participant U as Player
  participant W as Web app
  participant D as Database
  participant J as Job runner
  U->>W: POST checkout-sessions (cart, address, speed, coupon)
  W->>D: validate, price, store quote for 5 min
  W-->>U: session and totals
  U->>W: POST attempts (method CARD)
  W->>D: create attempt PENDING and PIN challenge
  U->>W: POST challenge/verify (PIN)
  W->>D: lock card, check PIN, mark authenticated
  Note over W,D: no money has moved yet
  U->>W: POST pay (Idempotency-Key)
  W->>D: pay transaction, all or nothing
  D-->>W: committed
  W-->>U: receipt, new balance, tracking
  D->>J: outbox row, picked up within a minute
  J->>D: notifications, stats, progression, cache purge

  HIDDEN --> PUBLISHED: appeal upheld
  PUBLISHED --> ARCHIVED: owner archives

Simple chains

ShipmentPlaced→Packed→Shipped→Out for delivery→Delivered

Stage times are fixed at purchase (Standard 24 h, Express 2 h, Zap 10 min). The current stage is worked out from the clock, so no job has to run.

Checkout sessionOpen→SucceededorCanceledorExpired after 5 min
Stock unitAvailable→Issued→Revoked (never resold)·Available→Retired unsold
CardActive⇄Frozen→Replaced (new card issued)
Admin sensitive actionQueued 24 h→ExecutedorCancelled
